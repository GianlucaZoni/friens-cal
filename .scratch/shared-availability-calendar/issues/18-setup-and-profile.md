# 18 — Setup flow and profile editing

Type: prototype
Status: resolved
Blocked by: —

## Question

Ticket 11 decided what the customisation step *contains*; ticket 13 deleted half
the screens this flow was once assumed to need. What remains is screen design.

1. **Sign in and sign up.** Email + password on an allowlist (ticket 02). No
   confirmation screen and **no password-reset flow** (ticket 13) — a forgotten
   password is reset from the Supabase dashboard when someone asks in the group
   chat, so the sign-in screen needs to say something honest about that rather
   than offering a dead "forgot password?" link. Blobatar's registry ships a
   `password-field` component.
2. **What a rejected email looks like.** The `before-user-created` hook rejects
   anyone not on the allowlist. That error surfaces mid-signup and needs copy
   that does not leak whether an address is on the list.
3. **Step 1 — display name and a randomised blobatar.** Ticket 11 requires this
   step to *materialise* the seed's hue and tone into columns, and to bias the
   initial hue away from hues already taken.
4. **Step 2 — customisation.** Live-preview blobatar with a hue slider, a
   six-swatch tone control, ten expressions, and reroll (ticket 11). Both steps
   show the avatar.
5. **The profile dropdown** behind the top-right blobatar, which reopens
   customisation and holds sign-out. Ticket 12 places the cluster; this decides
   what is inside the menu. **Sign-out is confirmed as living here** — the
   ticket 12 prototype flagged that it appears in the reference screenshot's
   blobatar menu but had never been written down anywhere.

## Answer

Prototype: `src/prototypes/setup-flow/` — five screens on one route,
`?screen=signin|signup|step1|step2|profile`. Standalone twin, no build step:
`src/prototypes/setup-flow/preview.html` (generated by `build-preview.mjs`,
which inlines the real `blobatar@2.7.0` bundles so every blob is drawn by the
library rather than imitated).

Findings: [`prototypes/18-setup-flow.md`](../prototypes/18-setup-flow.md).

### The flow

**Sign in.** Email, password, sign in. The space where a "forgot password?" link
would sit carries an honest sentence instead of a dead link — wording is the
human's call (below). Nothing else: it is four controls and it should stay that
way.

**Sign up.** Email, password, create account. No confirmation screen; a Friend is
signed in the moment the account exists. Rejection surfaces inline under the
fields as one message plus one secondary line, with both inputs marked invalid.

**Step 1 — name and blob.** Display name, one large animated blobatar,
"Try another", and a visible row of the hues already taken showing the new
Friend's starting angle and its distance from the nearest of them. That row is
what makes the bias legible as a *default*: the next screen's slider moves
anywhere, including onto someone else's hue. "Try another" **materialises** —
it writes `blobatar_seed`, `hue` and `tone` as values, never nulls.

**Step 2 — customisation.** One live-preview blobatar with the controls beside
it: a continuous hue slider (taken hues marked as ticks — labels, not walls), a
six-swatch tone segmented control rendering each swatch at the *current* hue,
ten expressions each drawn as your own blob in that pose, and reroll. Not a grid
of pre-rendered avatars. A small "where this colour shows up" strip (sidebar
row, Candidate glow, heatmap ramp) sits beside the preview, because "changing
your hue recolours your entire grid" is intended and a Friend should see it
while dragging rather than afterwards.

**Profile dropdown.** Identity (name + email), "How you look…", sign out.
Customisation reopens as a `Dialog` holding the same controls with the
walkthrough furniture stripped — not a route, not a settings page.

### Confirmed against the real library, not assumed

- **Reroll changes shape and never colour — ticket 11's claim holds.** Four
  seeds at a fixed `hue: 210, tone: 0.62` render byte-identical fills
  (`#0097aa`, `#051214`) and different geometry every time. The same four seeds
  *without* explicit hue/tone give four unrelated colours — which is exactly
  what step 1's materialisation prevents. Step 2 asserts it live: the stored
  panel flips to "HEAD MOVED — bug" if it ever stops holding.
- **Ten expressions, and exactly the four named tint.** `mad`, `love`, `shy`,
  `sick` are the only four carrying a `.tint`; the other ten render fills
  identical to `idle`. The exclusion list is correct and complete.
- **The ring already exists.** base-lyra's `Avatar` root ships
  `after:border-border after:mix-blend-darken dark:after:mix-blend-lighten`, so
  every `Blobatar` gets ticket 11's ring for free in both themes. Nothing to
  build. It is needed: pastel/pale/bright measure ~1.4–1.6:1 against a light
  surface and ink ~1.7:1 against a dark one.
- **`password-field` never landed.** Not in `src/components/ui/`, not in the
  installed list. Built from `InputGroup` + `InputGroupButton` instead, which is
  the sanctioned shape anyway; adding the registry item later is a swap.

### Corrections to earlier work

- **The six tone swatches are addressed off by one.** blobatar resolves tone with
  `TONES.find(([edge]) => v < edge) ?? TONES[0]`, so the numbers in that table
  are **band upper edges**, not swatch values. Passing `0.20` gives *pale
  neutral*, not pastel; passing `1.0` falls off the end and wraps to *pastel*,
  not ink. Ticket 11's own contrast paragraph names "an `ink` blob on a dark
  one" — the value that yields ink is `0.93`, not `1.0`. Store band interiors:
  `0.10 / 0.28 / 0.49 / 0.71 / 0.86 / 0.96`. Ticket 07 should constrain to those
  six values, not to `0..1`.
- **The drafted allowlist hook leaks.**
  `research/supabase-auth-and-rls.md` §1.4 ships
  `'That email is not on the list. Ask whoever set this up to add you.'` — the
  exact leak this ticket forbids. The rejection copy is a **SQL string in the
  hook**, not a React constant, so whichever draft wins must be pasted there.
- **Copy cannot close the enumeration leak on its own.** With Confirm Email
  disabled (ticket 13), an already-registered address returns Supabase's own
  `User already registered`, not the hook message — Supabase's enumeration
  protection was a property of the email we deleted. Only a client-side
  catch-all that replaces *every* signup error with one sentence closes it.
- **The ring is a disc frame, not a silhouette outline.** It says *where the
  avatar is*, not *what shape the blob is*. Since the settled collision decision
  leans on "the blobatar shape disambiguates", a pale-neutral blob is marginal
  at the 24px used in dense rows. Readable at 32px+. For ticket 12/15 to look at
  once real rows exist.
- **`npx tsc --noEmit` at the repo root checks nothing** — the root
  `tsconfig.json` is a solution file with `"files": []`. Use
  `npx tsc -p tsconfig.app.json --noEmit`. It currently reports
  `Type 'string' is not assignable to type 'Expression'` in two *other*
  prototypes: the HTTP-string-vs-React-object trap from the component inventory,
  hit independently by two agents. Promote it into whichever ticket builds the
  shared avatar component.

### Needs the human

**1. The dead-reset-link copy on sign in.** Three drafts, live on the screen —
`?screen=signin&copy=A|B|C`, or press <kbd>c</kbd>.

- **A — say it up front.** Always visible under the password field: *"Forgotten
  it? There is no reset email — ask in the group chat and someone will reset it
  for you."* Loudest; nobody hunts for a link that is not there, but every
  sign-in reads a sentence about failure.
- **B — link-shaped, honest inside.** A real link in the familiar place,
  *"Forgotten your password?"*, opening: *"There is no reset link. Say so in the
  group chat — whoever set this up resets it from the Supabase dashboard, and
  you sign in with the new one."* Keeps the expected shape; costs one click to
  learn the bad news, and the click looks like it might send an email.
- **C — only when it matters.** Nothing at rest; the sentence appears under a
  failed sign-in. Cleanest screen, but a Friend who gave up before typing never
  sees it, and "no reset email" is what they needed before the third attempt.

**2. The allowlist rejection copy.** Three drafts —
`?screen=signup&copy=A|B|C`. **This is a SQL string in
`public.hook_restrict_signup_to_allowlist`**, so choosing it means editing that
function, and the research's current draft must be replaced either way.

- **A — one message for every failure.** *"We could not create an account with
  those details."* / *"Everyone here was added by hand. If you think you should
  be in, ask in the group chat."* Leaks nothing because it is the same sentence
  for a bad password, a taken address and an unlisted one. **The only draft that
  also closes the `User already registered` leak**, and the only one that
  requires a client-side catch-all. Cost: a Friend who typo-ed their own address
  gets no hint that they typo-ed it.
- **B — name the gate, not the address.** *"Signing up here is invite-only."* /
  *"Accounts are created for addresses that were added by hand. If yours should
  be one of them, say so in the group chat."* Explains the rule without
  evaluating the address; reads best to an actual friend.
- **C — point at the chat and stop.** *"That did not work."* / *"Ask in the group
  chat and someone will sort it out."* Shortest and least revealing, also least
  useful — every failure becomes a message to a human.

**3. Does "change password" belong in the profile dropdown?** Not asked in the
ticket, and it is a genuine open question rather than a consequence of 13.
Ticket 13 deleted the *reset* flow — the emails, the `PASSWORD_RECOVERY`
handling, the two screens. It did not delete `updateUser({ password })`, which
works for an already-signed-in Friend with no email involved. So a Friend who
*knows* their password could change it without touching the dashboard, and the
dashboard round-trip would be needed only for a genuine forget. The prototype
leaves it out (fewer things to build, and a group of five will use the dashboard
route anyway) — but that is a default, not a finding.

**4. The two `oklch(L, C, hue)` constants per theme.** Ticket 11 fixes the form
and leaves the numbers to tickets 15 and 16. The prototype ships placeholders
(`light: L .58 C .15`, `dark: L .74 C .14`) purely so the sidebar row, glow and
heatmap strip could be drawn. Not a decision — flagged so nobody inherits them
by accident.

## Decisions

1. **Copy: draft A**, for both the dead-reset line and the allowlist rejection —
   chosen on the enumeration-leak argument, not on voice. Copy alone cannot close
   the leak: with Confirm Email off, an already-registered address returns
   Supabase's own `User already registered` regardless of what we write, and
   **only a client-side catch-all closes it — which is draft A's shape and no
   other's**. The rejection string lives in the `before-user-created` hook's SQL,
   so the chosen text must be pasted *there*; the research doc's current draft
   (`'That email is not on the list…'`) is the exact leak this forbids and must
   not be shipped as written.
2. **Change password ships**, in the profile dropdown. Ticket 13 killed the
   *reset* flow because it needs email; `updateUser({ password })` needs none and
   works for anyone who knows their current password. The dashboard is now only
   for genuinely forgotten passwords.
3. **Blobatar animation policy** (spans ticket 12):
   - the large preview avatar in **customisation** — `animate="always"`
   - the current Friend's avatar in the **top-right cluster** — `animate="always"`
   - **roster avatars in the left sidebar** — animate while the cursor is over
     the sidebar, and on mobile while the drawer is open
4. `password-field` never landed from the registry; built from `InputGroup`.
